# OshiDeck

YouTube Live Chatのコメントやメンバー絵文字の組み合わせを保存し、ワンクリックで呼び出せるChrome拡張機能です。

バージョンは `manifest.json` にあります ── ここに書き写すと、片方だけ古くなるので。
直した挙動は patch、見える変化は minor。配布されるファイルを変えて version を
据え置いたコミットは `tools/hooks/pre-commit` が止めます ── 一度、十四コミット
ぶん据え置いたままにしたので。
試用ZIPを渡した後の更新も、未commitの作業中であってもversionを上げます。
一度渡したバージョン名で別の内容を再配布しません。

## Features

- コメントやメン限スタンプの組み合わせを「札（カード）」として保存
- 札はカード名を持たず、中身そのものがラベル
- **手札モード** — 札が扇状に並ぶ。幅に合わせて1行の枚数が自動で増減（400pxで7枚、760pxで14枚）
- **リストモード** — 1行1枚。幅が広いほど欄が増える
- カードプール（保存した札はすべてここ）とデッキ（そこから選んで並べたもの）の2階層
- 同じ札を複数のデッキに入れられ、デッキごとに別の位置を持てる
- 編成ページで保存済みの札を共通・チャンネル専用に変更。他のデッキから外れるときは対象を確認
- チャンネルごとの推し色が札の上端に出る
- 並び順は「チャット連動 / 最近よく使う順 / 使った回数順 / 自分で並べた順」── 既定はチャット連動
- **チャット連動** — いまチャットで流れている反応に合う札を前に出す
- **チャットから引く** — 部屋が沸いたとき、持っていない反応を1枚だけ手札の左に差し出す
- **スタートデッキ** — そのチャンネルの常連が使っている札を、まとめて、または1枚ずつ
- 同じ札を何度も繰り返す札は `🪽🫧🎶×2` と数えて出す
- 標準の絵文字は、チャットが実際に描いているYouTubeの画像で出す
- 使った回数はチャンネルごとに数える
- クリックで入力欄へ、`⇧` ＋ クリックでその場から送信
- メン限スタンプは持ち主のチャンネルを判定し、送れない配信ではロック表示
- 削除は取り消しトースト付き（確認ダイアログでページを止めません）
- YouTubeのライト／ダークテーマに追従（手札・リスト・保存メニュー・チャット上の追加ボタン）
- スーパーチャットが同じ隅を使うときは、パネルのほうが身を引く
- チャットの「編成」から開くと、そのチャンネルのデッキを直接選択（未作成なら空のデッキを作成）
- うまくいかないときのための診断ログ（設定ページから書き出せます）
- JSONでの書き出しと読み込み（追加 / 全部置き換え）
- 初回の同意後にチャットを読み取り、札・設定・診断ログをブラウザ内に暗号化して保存

## Install

1. このリポジトリをCloneまたはDownloadします。
2. Chromeで `chrome://extensions/` を開きます。
3. 「デベロッパー モード」をオンにします。
4. 「パッケージ化されていない拡張機能を読み込む」を選択します。
5. OshiDeckのフォルダを選択します。
6. OshiDeck の設定でデータの利用方法を確認し、「同意して有効にする」を選びます。
7. YouTube Live / Premiere のチャットを開きます。

テーマの文字コントラストは `npm run test:theme` で実物のChromeを使って検査できます。
Chromeの場所を自動検出できない環境では `CHROME_BIN` を指定してください。
ライト→ダーク→ライトの切り替えと、YouTubeの色変数がない場合のフォールバックも対象です。

## Release build

Node.js、Git、`zip`、`unzip` がある環境で、次を実行します。

```sh
npm ci
git config core.hooksPath tools/hooks
npm test
npm run build
```

出力は `dist/oshideck-<version>.zip` と、ファイル一覧・サイズ・SHA-256を記録した
`dist/oshideck-<version>.manifest.json` です。version は `manifest.json` から読みます。
ZIPのルートに `manifest.json` があるので、展開したフォルダをChromeに読み込めます。

収録するのは、明記した実行用JS・CSS・HTML、PNGアイコン4サイズ、`presets/index.json` と
そこに載っているセットです。採掘用チャット、登録チャンネル一覧、色調査CSV、参考画像、
`.env`、Gitの管理情報、テストと依存パッケージは配布対象外です。入力ファイルは変更しません。

ビルド時に、manifest・設定ページの参照先、JSの静的importと再export、セットの形とチャンネル専用scope、スタンプ画像のHTTPS URL、
本機パス・アドレス・既知の秘密値・端末のアカウント名を検査します。未commitの変更も対象です。
アカウント名の規則はcommit hookと同じで、短すぎる名前は対象外、文字列として大文字小文字を区別せず照合します。
公開名の例外は `tools/hooks/public-names.tsv` の「パス＋元の行バイト列のSHA-256」だけに適用し、
アドレス・パス・秘密値は常に検査します。例外一覧が読めない、または形式が不正ならビルドを止めます。
ZIPを作った後も、名前とサイズ、CRC、
全ファイルのSHA-256を読み戻して確かめます。ZIPの余分なメタデータを外し、時刻と権限を
固定するので、同じ環境で同じ内容から作れば同じバイト列になります。

HTMLの検査には `parse5` と `html-encoding-sniffer` を使うため、先に `npm ci` が必要です。
検査中にスクリプトや通信は実行しません。UTF-8のHTMLを対象に、template・宣言的shadow DOM内の
参照とSVGのscriptも検査します。古いparserが捨てるタグ、不完全なraw text要素、複数のbaseや
参照より後のbaseなど、解釈を保証できない書き方は明示的に拒否します。
HTMLは1 MiB・開始／終了タグ合計20,000個までに制限します。これらの開発用依存はZIPには入りません。

### GitHub Actions

`main` への push と pull request では、Node.js 24 でテストと Chrome のテーマ検査を実行し、
配布用 ZIP を作って検証します。リリース時は `manifest.json` と同じバージョンのタグを push します。

```sh
git tag -a v1.0.0 -m 'OshiDeck 1.0.0'
git push origin refs/tags/v1.0.0
```

タグの検査が通ると、GitHub Actions がタグの注釈をリリースノートに使い、
ZIP と SHA-256 が入ったファイル一覧を添付した Release の下書きを作ります。
公開する前に下書きの内容を確認してください。

直近の配布内容の変更は次のとおりです。

- 初回の同意までチャットの読み取りと診断ログの記録を待つ。同意後に旧バージョンの札・デッキ・設定・診断ログを、AES-GCM で暗号化したブラウザ内のデータベースへ移行
- YouTube ページへのアクセスを `content_scripts.matches` の宣言に統一
- 抽札では繰り返し回数だけが違う反応を既存の札として扱う（👏×5を持っていれば👏×6は引かない）。保存内容と送信時の回数は変更しない
- 編成ページの札に保存範囲の切り替えを追加。他のチャンネルから外れる場合は一覧で確認してから適用
- スタートデッキを新版に置き換え、新しく作る札をチャンネル専用に統一。内容が一致する既存の共通札は優先して再利用
- 代表色と白・黒・灰の初期色、彩雲ののの虹色シャボン玉マーク（地色は選んだチャンネル色に追従）、虹深°ぬふの髪飾りを模した選色器
- 操作結果・現在の状態・失敗理由を残す診断ログ。本文は記録せず、共有前の説明にチャンネル・動画IDとメンバー判定を明記
- 編成ページの取り消し通知を画面下に固定。10秒の表示時間はホバー・キーボードフォーカス中に停止
- 色相の丸めが360度になった場合は0度に戻し、ぬふの選色器も白・黒・灰を実際の色で表示

## Usage

1. YouTubeの通常のチャット入力欄でコメントを作ります。
   - `🦢✨🦢✨🦢✨`
   - `👏👏👏👏👏`
   - `はい！はい！はい！はい！`
   - YouTubeの絵文字ピッカーからメン限スタンプを並べてもOKです。
2. OshiDeckの「保存」を押すと、そのまま札になります。名前を付ける必要はありません。
3. 配信ページで保存した札はそのチャンネルのデッキに入り、次に同じチャンネルを開くと自動で出てきます。
4. 札をクリックすれば入力欄へ復元、`⇧` ＋ クリックでそのまま送信。

札の上端の色がスコープです — グレーが共通デッキ、色つきがそのチャンネルの札。色はチャンネルごとに自動で割り当てられます。

## Auto Send

設定ページの「札をクリックしたら自動で送信する」をオンにすると、札を入れた直後に送信します。初期値はオフです。

オフのままでも `⇧` ＋ クリックでその場から送信できるので、普段は入力欄に入れるだけ・確信があるときだけ即送信、という使い分けができます。

## Notes

OshiDeckはYouTubeの公開APIではなく、Live ChatのDOMを利用しています。
そのためYouTube側のHTML構造が変更された場合、調整が必要になる可能性があります。

メンバー絵文字はYouTubeが入力欄で使用している以下のDOM形式を再現しています。

```html
<img
  class="emoji yt-formatted-string style-scope yt-live-chat-text-input-field-renderer"
  src="..."
  alt="..."
  data-emoji-id="..."
>
```

### Scope survives everything

保存された scope は、その札に何ができるかを決める唯一の答えです。ただし
**メン限スタンプのほうが強い** —— 古いビルドや手で書き換えたバックアップが
「メン限入りなのに共通」という札を持ち込んでも、内容から強制的に上書きします。

過去のどの形式から移行しても、当時の意味をそのまま引き継ぎます。

| 形式 | 何が「そのチャンネルの札」を表していたか |
| --- | --- |
| v0.1 / v0.2 | `presets.channels[X]` に入っていること |
| v0.3 | 札の `scope` フィールド（今と同じ意味） |
| v0.4 以降 | メン限スタンプを含むこと |

読み込み時に、そのデッキが送れない札への参照は落とします。古いビルドが作れた状態で、
画面にも出せず操作もできないためです。

バックアップは format 2 になりました。format 1 も読めますが、そちらには scope が
無いので当時の意味（メン限入り＝専用、それ以外＝共通）で補います。

## Which deck a card goes to

保存先は押すボタンで決まります。上の帯は入力欄の中身に合わせて姿を変えます。

```
入力欄が空のとき   ● さくらチャンネル ＋ ● 共通   14枚          [編成]
何か入力したとき   保存先  [＋ さくらチャンネル] [＋ 共通]      [編成]
札が1枚も無いとき  コメントを入力して保存すると札になります      [編成]
チャンネル不明時   チャンネルが分かりません
たたんだとき       ● さくらチャンネル ＋ ● 共通   14枚 ▾        [編成]
```

下の2行はもともと帯の下に**もう1行**として出ていました。帯があり、説明の行があり、
その上下に余白がある ── 高さ400pxのチャット欄で、**新しいデッキが見せるものの大半が
それ**でしたし、ポップアウトしたチャット窓（持ち主を特定できないので永久にデッキを
持てません）が見せるものは**それだけ**でした。

なので文は帯の行に移し、下の行は消しました。パネルごと消せないのは、編成への入口が
ここにしか無く、入力した瞬間に保存先が出るのもここだからです。空のときは `#oshideck-root`
に `data-empty` が付き、自分の余白も帯の下限も詰めます。

手札の設定行数やリストの表示枠を超える札は、同じ領域を縦にスクロールして使えます。
札はすべて描画し、展開・折りたたみの操作を挟まず最後の札まで届きます。

## Folding it away

同じ一行に、**自分から**なることもできます。デッキの名前が出ているその行が、
そのままパネルをたたむ取っ手です（右端の `▾`／`▴`）。押すと手札もチャットが引いた札も消えて、帯だけが残ります。

帯に**ボタンを足さなかった**のは幅の問題です。帯の一行の文は、横のボタンが残した
分だけに切り詰められます ── いちばん余裕の無い文で**6.8px**しか空いていないので、
ボタンをもう一つ置けば何本かは語の途中で切れます。デッキの行そのものを取っ手に
すれば幅はゼロで、しかも帯でいちばん広い的になります。

状態は `settings.folded` に**書き残します**。だから「普段はたたんでおく／開いて
おく」の設定は別に要りません ── 最後にそうしておいた状態が、そのまま次の配信での
普段の状態です。オプション画面にも項目は置いていません。

二つだけ例外があります。

* **空のとき**はたたみません。すでに一行ですし、そのときの一行は説明文であって
  デッキではないので、**開き直す取っ手がそこに無い**からです。
* **カードプールを開いているとき**もたたみません。自分で開いた場所で、出口は
  その[閉じる]ボタンのほうです。

`settings.folded` は `panelSignature` にも入っています。パネルは署名が変わらない
描画を飛ばすので、入れ忘れると `▾` を押しても何も起きません。

| | 上下の余白 | 説明の行 | 帯の下限 |
|---|---|---|---|
| 前 | 7px+5px | 余白16px＋一行 | 24px |
| 後 | 3px+3px | **無し** | 20px |

以前の結果（**実測**、Chromium 148・オフラインのフィクスチャで本物のCSSと render を使用）：

| | 空のとき | スタートデッキの誘いあり |
|---|---|---|
| English | **29px** | 49px |
| 日本語 | 34px | 54px |
| 繁體中文 | 34px | 54px |

フィクスチャでの値です ── YouTubeに実際に差し込んだときに継承されるスタイルまでは
まだ確かめていません。前の高さだけは計算値で、英語なら約64px（うち説明の行が約29px）、
スタートデッキ込みで約84px。
帯そのものは23px ── 中のボタンの高さ ── なので、下限を24→20に下げて得られるのは1pxです。
効いているのは余白と、消えた一行のほうです。札が入ればどちらのモードも 7px/5px、
リストモードは 7px/7px にきちんと戻ります。

0.51.2では配布ZIPを展開し、macOSのheadless Chrome 157に拡張機能として読み込んで再確認しました。
幅400px・英語の制御用チャットページで、折りたたみ時は**31px**、チャンネルを判別できず
操作を止めた状態は**27px**でした。後者には[編成]などのボタンがありません。
同じ条件での日本語・繁體中文の高さと、実際のYouTubeチャット内の高さは未測定です。

帯のボタンは**数を99で打ち切ります**（`MOST_SHOWN`）。`プール10000`と出すと文のほうから
23px奪って切り落とすからで、1万枚のプールは荒唐無稽でもありません ── その大きさの
バックアップは検証を通りますし1MB未満です。`tools/check-width.mjs` はこの上限を
**content.js から読んで**ボタンの最大幅を出すので、予算とボタンが食い違えません。

どちらの文かは区別します。チャンネルが分からないときは**何もできません**（次の節）。
「保存すると札になります」と言えば、できないことを勧めたうえに、肝心の「なぜ空なのか」を
答えないままになります。ポップアウトしたチャット窓はこの状態のまま変わらないので、
なおさら言うべきはそちらです。

札のスコープ帯（手札モードなら上端、リストモードなら左端）は**読むためのもの**です。
保存したあとでも、編成ページで札にポインターを重ねると出る右上の「⇄」から変更できます。
キーボードでフォーカスしたときも表示され、ツールチップに「共通にする」「専用にする」と出ます。
共通から専用にするとき、他のチャンネルのデッキにも入っている札は、対象のチャンネルを
一覧で示してから確認します。「専用にして外す」を押すまで変更しません。

メン限スタンプ入りの札は共通デッキに入れられません。配っているチャンネル以外では
そもそも送信できないためで、「共通」ボタンは無効になり、理由がツールチップに出ます。

## チャンネルが分からないときは動きません

このパネルがすることは、すべて**チャンネル一つ**についての話です。デッキはチャンネルの
ものですし、プールの札もチャンネルに対して保存されます。持ち主を特定できなかったページでは
どの問いにも答えが無いので、**パネルは止まります**。帯の一行がその理由を言って、それだけです。

止まるのは具体的にこれだけあります。

| | 以前 | いま |
|---|---|---|
| チャットからの抽札 | 引いていました | **引きません** |
| コメント横の `＋` | 出ていました | **出ません** |
| 入力中の保存先 | [プールに保存] | **出ません** |
| [編成]ボタン | 出ていました | **出ません** |
| 帯の一行 | 「チャンネルが分かりません」 | 同じ |

抽札だけは、やめたというより**間違っていました**。送れるかどうかを判定する
`whyNotSendable` は、チャンネルを渡されないと「**no**」ではなく「**判定できない**」を
返します ── つまり `""` です。offerFromChat はそれを「送れる」と読むので、持ち主の
分からないチャットでは**他所のメン限スタンプ**まで条件を全部すり抜けて差し出されていました。
押せばその場で失敗する札です。

`＋` も同じ筋です。`＋` が保存する先は札で、札はチャンネルに対して保存されるので、
「ここでは何もできません」と帯が言っている横で、チャット中の全コメントに `＋` が
乗っているのは矛盾です。判定は `grabFor()` という名前の関数に出しました ──
`onPageChanged` と同じ理由で、リスナーの中に書いてあると**テストから呼べない**からです。

`settings.folded` でたたむのとは別の状態です。たたんだ一行には開き直す取っ手が
ありますが、ここの一行は説明文なので取っ手はありません（[Folding it away](#folding-it-away)）。

デッキ編成はオプションページにあるので、拡張機能のアイコンからは開けます。
配信ページの[編成]ボタンが消えるだけです。

### 描き直しでは届かないものが二つあります

パネルを描き直しても消えないものが二つあって、止めるときに**自分で戻さないといけません**
（どちらもレビューで見つかりました）。

* **開いたままのカードプール** ── `poolOpen` は描き直しをまたいで残ります。チャンネルを
  見失った瞬間、帯には「プール / スタートデッキ」のタブが出たまま、[閉じる]ボタンだけが
  （他の操作と一緒に）消えて、**出られなくなっていました**。しかも帯が理由を言う行に
  ならないので、何が起きたのかも分かりません。止めるときに `poolOpen = false` にします。
* **もうチャットに出ている `＋`** ── `＋` はYouTube側の行の中にいて、パネルの中にはいません。
  だから描き直しても触れません。`grabFor()` が決めるのは**次に**どこへ出すかだけなので、
  ポインタが動かなければ古い `＋` がそのまま残り、押せば保存先まで開きました。
  止めるときに `offerGrab(null)` で引き取ります。

### 遅れて分かるチャンネル

配信ページの、チャンネルIDを持っている部分はチャットより**あとで**埋まることがあります。
そのために600msで5回だけ訊き直していました ── そのあとは**永久に諦めて**いました。

パネルがチャンネル無しでも動いていたころは、それで済んでいました。いまは止まるので、
「3秒遅れて分かる」と「1分遅れて分かる」の差が、**パネルか一行か**の差になります。
しかも他に気づくものがありません ── 抽札オフ＋手動の並び順なら静かなチャットは自分では
描き直しませんし、ページのオブザーバは入力欄とメンバーバッジしか見ていません。

なので5回のあとは**5秒おきに訊き続けます**。諦めないことの代償はゼロです ──
永久に分からないほう（ポップアウトしたチャット窓）には**動画IDが無い**ので、
そもそも1回目の前に return しています。

一つだけ隙があります。`＋`（またはチャットが差し出した札）を押して保存先を選ぶまでの
間にチャンネルが分からなくなった場合、`saveTokens` はその時点でページをもう一度読むので、
共通札としてプールに入ります（`saved.pool`）。出した時点では押せたボタンなので、
掴んだコメントを捨てるより保存するほうを選んでいます。

残しているものが一つあります。**チャットの集計そのものは止めていません**
（`src/trending.js`）。チャンネルは遅れて分かることがあり（`retryUnresolved`）、
そのときに手ぶらで始めるより、それまでの数十秒を持っているほうが良いからです。
分かった瞬間から普通に引きます。

## One writer

配信ページのパネルと編成ページは同じデータを変更しますが、**どちらも直接は書きません**。

`chrome.storage` には compare-and-set がありません。両方が read を終えてから
どちらかが write すると、負けた側の変更は跡形もなく消えます。実際に測ると、
使用回数の記録と並べ替えを同時に走らせただけで片方が失われます。

そこで変更は「名前の付いた操作」として service worker に送り、worker が
**1つずつ順番に**最新状態へ適用します（`background.js` のキュー、`src/store.js` の `OPS`）。

```
content.js ─┐
            ├─→ chrome.runtime.sendMessage({ type: "mutate", op, args })
options.js ─┘        ↓
              background.js  … 直列キュー
                     ↓
              read → 適用 → 1回の set()
```

守っていること。

- **1操作 = 1回の `set()`**。互いを参照する `cards` と `decks` が食い違う瞬間がありません。
  ドラッグでの「追加して位置を決める」も、読み込みも、1操作です
- **判断も worker の中で**。重複の有無、そのチャンネルで使える札かどうか、
  バックアップのマージ結果 —— どれも呼び出し側のスナップショットではなく、
  worker が読み直した状態に対して決めます
- **取り消しも操作**。押すまでの間に相手が動いていても、消えた札は戻さず、
  すでに戻っていれば二重に入れず、その後に付いた名前や色は巻き戻しません
- **`read()` は読むだけ**。古い形式からの移行もメモリ上で行い、
  最初の操作が worker 側で書き込みます
- 書き込みに失敗したら入力欄は消さず、成功したとも言いません

`settings` も同じ経路です。直接書いていたころは、設定のクリックと読み込みが重なると
あとから着いたほうがもう片方を消していました。

### Two kinds of card

札は「**共通**」か「**そのチャンネル専用**」のどちらかです。これは内容から推測するもの
ではなく、**保存するときに選ぶ札自身の性質**です。

```
保存先  [＋ さくらチャンネル] [＋ 共通]
```

- **共通** — どのチャンネルのプールにも出て、どのデッキにも入れられます
- **チャンネル専用** — そのチャンネルのプールにしか出ません

`888` のような普通のテキストでも「さくら専用」にできます。逆に、メン限スタンプを
含む札は**共通にできません**（他のチャンネルでは物理的に送れないため）。その場合は
「共通」ボタンが無効になり、理由が出ます。

編成ページでは、デッキ・プールのどちらの札からも保存範囲を変更できます。内容と使用履歴は
そのまま残ります。共通から専用への変更で他のデッキから外れる場合は、対象を一覧で確認してから
適用します。確認中に別のデッキにも追加された場合は、改めて確認します。
メン限スタンプ入りの札は「共通にする」が無効になり、理由がツールチップに出ます。

配信ページ以外ではチャンネルが分からないので、**パネルごと止まります**
（[チャンネルが分からないときは動きません](#チャンネルが分からないときは動きません)）。

## Pools are per channel

プールはチャンネルごとにあります。中身は「**どのデッキでも使える札**」＋「**そのチャンネル専用の札**」。

```
さくらのプール:  888  わこつ  [さくらのスタンプ]
ゆめののプール:  888  わこつ  [ゆめののスタンプ]
                 └─ 共通札はどのプールにも出る
```

他のチャンネル専用の札は出てきません。見えても使えない札が並ばないので、
プールに入っているものは必ず今のデッキに入れられます。

そのおかげで「外す」の意味がどこでも同じになります。デッキから外した札は
自分のチャンネルのプールに戻るだけで、消えることも、行方不明になることもありません。

| 場所 | できること | 影響 |
| --- | --- | --- |
| 配信ページ | 打つ / 編集 / **⏏ このデッキから外す** | このデッキだけ |
| 編成・デッキ欄 | **⏏ 外す** | このデッキだけ。札はプールへ |
| 編成・プール欄 | **× 削除** | すべてのデッキから消える |
| 編成・左の一覧 | **× デッキごと削除** | 共通の札は残り、**そのチャンネル専用の札は一緒に消えます** |

取り返しのつかない削除は編成ページのプール欄だけに置いています。すべて「元に戻す」が付きます。

## Pool and decks

保存した札はすべて**カードプール**に入ります。**デッキ**はそこから選んで並べたもので、
配信ページに出るのはデッキだけです。プールに入れただけの札は自動では出てきません。

```
カードプール          888  わこつ  はいはい  🎉  おつかれ  GG
                       │      │        │
さくらチャンネルのデッキ   888  はいはい   🎉
ゆめのチャンネルのデッキ   GG   888
```

- 同じ札を複数のデッキに入れられます
- **並び順はデッキごと** — 同じ札がさくらでは先頭、ゆめのでは末尾、ということができます
- **使った回数もデッキごと** — 下記
- **デッキから外す**（⏏）とプールに残ります。**削除**（🗑）はプールから消え、すべてのデッキから外れます
- 配信ページで保存すると、プールに入ると同時にそのデッキにも入ります（2手間にしないため）
- すでにプールにある札と同じ内容を保存すると、複製せずにその札をデッキに入れます

配信ページのパネルからは帯の「プール N」を押すと開き、札をクリックするとデッキに
入ります。全部の編成は設定ページで行います。

### どれだけ使ったかは、チャンネルごとの話です

使った回数は札の性質ではなく、**その部屋での習慣**です。`👏` をあるチャンネルで50回押したことは
隣のチャンネルについて何も言っていないのに、1つの数を共有していたころは、**そこで一度も押した
ことのない札が手札の先頭に居座って**いました。

なのでカードは `by` の下にチャンネルごとの数を持ちます。チャンネル限定の札はもともと
チャンネルが1つなので、そちらは何も変わりません。「最近よく使う順」「使った回数順」も、
編成ページの「$1回」も、いま見ているチャンネルの数を読みます。

**移行。** 以前の数がどのチャンネルで稼がれたものかは復元できません。そこで**その札が入って
いるデッキすべてにそのまま引き継ぎます** ── デッキ1つに入っている札（大半がそうです）なら
それが正解ですし、複数に入っている札でも、アップグレードで並び順を捨てない唯一の答えです。
次に押した時点から別々に育ちます。どのデッキにも入っていない札でも、**チャンネル専用なら
その数は残ります** ── そのチャンネルでしか使えなかったのだから、使われた場所は分かります。
共通の札だけは置き場所がないので落とします。

### まだ持っていない札も、そこから入れられます

入口はひとつですが、中は**2つに分かれています**。帯のラベルで切り替えます。

```
[手持ち 12][スタートデッキ 10]                      [閉じる]
```

- **手持ち** ── 保存してあって、このデッキには入れていない札
- **スタートデッキ** ── このチャンネルの常連が使っている札の**一組まるごと**（デッキに入れたものを除く）

プールにいるあいだはどちらも**破線の縁**です ── 引いた札と同じ意味で、押すまではデッキの
ものではありません。どちらの札かはラベルが言うので、札そのものには印をつけません。

**色帯はプールでも scope を言います。** 以前は「見ているだけでまだ出ていない」という理由で
プール内は全部グレーに塗っていましたが、入れるかどうかを決めている最中こそ scope が要る
情報です ── チャンネル限定の札はここでしか使えません。スタートデッキ側はなおさらで、その札は
一度も見たことがないので、ほかに手がかりがありません。

混ぜては置きません。保存した札とスタートデッキが提案している札は別のもので、ひとつの列に
並べると「プールに入っていないのにプールにある札」になってしまいます。

**同じ札が両方に出ることはあります。** 2つは排他ではなく、**2つの問い**です ──
「手持ち」はその札がどこから来たか、「スタートデッキ」はこのチャンネルの常連も使っているか。
持っているからといってスタートデッキから抜くと、10枚のうち7枚を自分で保存した時点で
スタートデッキは3枚として読めてしまいます ── 自分が同意した場所にだけ穴の空いた一覧です。

帯の入口のボタンが数えるのは**札の数**で、ラベルの足し算ではありません。10枚のうち9枚を
すでに持っていてデッキには入れていないなら、ラベルは［手持ち 9］［スタートデッキ 10］でも、
入れられる札は**10枚**です ── 19枚ではありません。手持ちだけを数えると、まだ何も保存して
いないチャンネル ── どのチャンネルも最初はそうです ── で入口そのものが出なくなります。

スタートデッキはもともと**全部か無か**で、しかも**デッキが空のあいだだけ**でした。10枚まとめて
入れるか何も入れないかで、自分の札を1枚入れた時点で入口が永久に消えます。スタートデッキが
何であるかから、そうなる理由は何もありません ── スタートデッキは札の一覧で、プールは札の
出どころで、まだ持っていない札も「このデッキに入れられる札」です。

まだ持っていない札を1枚だけ押したときも通るのは `loadPreset` です。全部入れるときと同じ道
なので、同じ内容の札をすでに持っていれば新しく作らずそれを使う、という判断もそのまま効きます。

すでに持っている札は、スタートデッキ側でも**あなたのその札**として出ます ── こちらは
`loadPreset` ではなく `addToDeck` で、その ID も色もこのチャンネルで稼いだ回数も持ったまま
デッキに入ります。同じ言葉の2枚目は作りません。
デッキに入っている札はどちらにも出ません ── プールは「まだ入れられるもの」です。
**同じ言葉かどうかで見ます。** デッキが持っているのは ID の一覧ですが、同じ言葉を別の ID で
2枚持っていることはある（このチャンネル用に1枚、どこでも使える札としてもう1枚）ので、
ID で訊くとデッキにある言葉のもう一方が提案され、押すと同じ言葉が2枚入っていました。

## Arranging from the stream

並び順が「自分で並べた順」のときは、配信ページのパネルでも札をドラッグして並べ替えられます。
編成ページを開かずに、配信を見ながら直せます。並び順はそのデッキだけのものなので、
他のチャンネルの見え方には影響しません。

配信ページで掴めるのは手動モードだけです。他のモードは反応や使用の重みで位置が変わります。
編成ページで決めた順はすべてのモードの同点時の基準で、重みが無ければそのまま表示します。

クリックは従来どおりです。ブラウザのドラッグは数px動かして初めて始まるので、
配信中に押した札が「送信されずにドラッグになる」ことはありません。

## Deck builder

編成ページの操作通知は**ウィンドウの下端から20px**の位置に固定します。
スクロール中も見える場所で、本文が長いときは本文だけを省略し、「元に戻す」と閉じるボタンは残します。
操作通知は通常10秒（設定保存の表示は1.2秒）で消えますが、ポインターが重なっている間と、通知内にキーボードのフォーカスがある間は
残り時間を止めます。表示時にフォーカスやスクロール位置を変えません。

取り消せるのは最後の操作ひとつです。古い通知のボタンや遅れて戻った取り消しの結果で、
新しい通知を変えることはありません。設定の保存表示も、取り消しの入口を消さないようにします。

設定ページの上段が編成ページです（配信ページの「編成」ボタンから開きます）。
左からデッキ一覧・選んだデッキ・カードプールの3列。

```
デッキ
┌──────────┬────────────────────┬──────────────┐
│● さくら 12│ さくら              │ カードプール 9枚│
│● ゆめの  8│ 推し色 ●●●●●●       │ 🔍 絞り込む    │
│● ほしの 15│ ┌────┐┌────┐      │ ┌──┐┌──┐    │
│          │ │ 888││はい │      │ │おつ││GG │    │
│          │ └────┘└────┘      │ └──┘└──┘    │
│          │   ↑ ここに落として追加 │   ↑ ここから  │
└──────────┴────────────────────┴──────────────┘
```

プールを横に置くのは、そこからデッキへドラッグするのが編成の主な動作だからです。
縦に積むと、掴んでから落とすまでにスクロールが要ります。

推し色はチャンネル名の**下**に置いています。横に並べると見出しが幅を食い、
中央の列が細くなって札が1行に1枚しか入らなくなります。

設定の節も同じページ幅にそろえ、端を合わせています。中の行は1列のまま。
2列に畳むと、説明がいちばん長く選択肢も多い「並び順」がいちばん窮屈になりました。

- **プールからデッキへドラッグ** — 札の間に落とせば、その位置に入ります。追加と並べ替えが1動作
- **デッキからプールへドラッグ** — そのデッキから外れます
- **デッキ内でドラッグ** — 並べ替え
- 絞り込みはプールにかかります（探すのはこれから入れる札なので）
- 削除・デッキから外す・プールから追加した操作は、画面下部の通知にある「元に戻す」で取り消せます

### What the pool shows

プールはそのチャンネルに**まだ入れられる札**です。デッキに入れた札はプールから消え、
外せば戻ってきます。プール ＋ デッキで、そのチャンネルで使える札の全部になります。

出てくるのは「どのデッキでも使える札」と「そのチャンネル専用の札」だけ。
他のチャンネル専用の札は、見えても押せないので出てきません。

## Presets

そのチャンネルの常連が使っている札を差し出します。**まとめて一組**か、**プールから1枚ずつ**かの
どちらでも入れられます ── デッキが空のときはまとめて入れるボタンが出ますし、そうでなくても
プールの「スタートデッキ」側にいつでも並んでいます（[Pool and decks](#pool-and-decks)）。

「デッキが空のとき」は**デッキの中身だけ**の話です。チャットが差し出した札は帯の下に出ますが、
それは**デッキに入っていません** ── 借りているだけで、持ち時間が切れれば消えますし、[取っておく]を
押すまで誰のものでもありません。以前はこれを「空ではない」と数えていたので、まとめて入れるボタンが
**チャットの流れ次第で出たり消えたり**していました。デッキを作り始める新しいチャンネルで、
いちばん起きやすい状況です。いまは札の**下に**そのまま残ります。

同梱しているのは**2,671組**、27,527枚。歌枠を中心に過去のチャットから掘ったものです（下記）。

**スタートデッキはバックアップではありません。** バックアップは自分のところへ帰ってくるもので、ID も
使用回数もどのデッキが何を持っていたかも丸ごと戻します。スタートデッキは**他人のところへ行く**ので、
持っていくのは中身だけです:

- **IDは持っていきません** ── 読み込むたびに作り直します。保存はそれぞれの端末の中だけなので、
  同じIDが他人に届くわけではありません。困るのは**自分の中**で ── 同じスタートデッキを2回読んだり、
  あとでバックアップを合流させたりしたときに、別物であるべき2枚が同じ札として扱われます
- **使用回数も履歴も持っていきません** ── あなたがよく使ったことは、配った先には関係がありません
- **書き出しは元の `scope` を記録します** ── ファイルとしては `global` / `channel` を読めますが、
  スタートデッキから新しく作る札は読み込み先のチャンネル専用です。既に同じ内容の共通札を
  持っているときは、その札を使います

### 二種類あります

| | 名乗るチャンネル | メン限スタンプ | どこで出るか |
| --- | --- | --- | --- |
| **持ち運べるほう** | なし | 入りません | どのチャンネルでも |
| **そのチャンネルのほう** | `channel: "UC…"` | **そのチャンネルのものは入ります** | そのチャンネルだけ |

メン限スタンプを外していたのは、**スタートデッキが持ち主を名乗れなかったころの理屈**でした。どこにでも
配られる可能性があるなら、一箇所でしか使えないものは持たせられません。名乗れるなら話は別で ──
渡す相手は同じ配信者を見ている人たちなので、**その人もメンバーかもしれない**。外したままでは、
デッキの中でいちばん手間のかかった部分をまるごと捨てることになります。

書き出すと**自動でそうなります**。デッキにそのチャンネルのメン限スタンプが1枚でもあれば `channel`
が付き、無ければ付きません（名乗れば他所では出なくなるので、理由もなく狭めません）。

メンバーでない人が読み込んだら、その札は**鍵がかかって手札の最後に並びます**
（[Member emoji](#member-emoji)）── 消えはしないので、メンバーになればそのまま使えます。

よそのチャンネルのメン限スタンプは、名乗ったあとでも入りません。読み込み側も同じ判断をするので、
手で書き換えたファイルを別のチャンネルに読ませても、送れない札は入りません。

**書き出しと読み込みは、デッキの上にあります。** 編成ページの、デッキの名前の右にある2つの
小さなボタンです ── バックアップの節ではありません。あちらは**全体**（プール・全デッキ・設定）を
まとめて扱うもので、こちらは**このデッキ1つ**。同じ並びに4つ置くと、どれがどこまで効くのかは
ラベルを全部読まないと分からなくなります。

読み込みは、渡された側から見た同じ動作です。ファイルは拡張機能自身の検証を通り、
**よそのチャンネル専用のファイルはその場で断ります** ── 黙って読み込むと、いちばん手間の
かかったところ（メン限スタンプの札）だけが消えて、残りが入ってしまうからです。

### 何を言っているかを数える

スタートデッキは、Holodex の活動中チャンネル一覧を固定して、歌枠と通常配信を分けて掘ります。
一覧を作業ディレクトリの `channels.json` に置いてから、次の順に実行します。

```
node tools/produce-presets.mjs --run chat-presets-YYYYMMDD --plan
node tools/produce-presets.mjs --run chat-presets-YYYYMMDD --mine
```

計画・取得結果・候補はチャンネルごとに残り、途中で止めても再開できます。取得失敗は
「チャットなし」と区別して記録します。ダウンロードは2並列、解析は1本ずつです。

- **歌枠は新しい2配信まで。** 40分〜16,000秒で、Holodex にコラボ相手の記載がないものを使います。
- **割合は人数。** その配信で発言した人数を分母に、その句を使った人数を数えます。
  2配信あれば両方に現れ、割合の平均が10%以上の札を残します。1配信ならその配信で10%以上です。
- **合格した歌枠の札は全部。** 10枚を超えても切りません。10枚に足りないときは通常配信から補います。
- **通常配信は13配信まで。** 2人以上が使い、3配信以上に出た候補を、2番目に人数の多かった配信の
  人数・延べ人数・送信回数の順で並べます。歌枠と同じ句は重ねて入れません。

最低人数の追加条件は設けていません。歌枠の発言者が10人以下なら1人の発言でも10%に届くため、
小標本のセットは内容の確認が必要です。札数を10枚で打ち切ることでは解決しません。

メン限スタンプも、そのチャンネルのものを拾います。削除済みのスタンプが独立した `□` の run に
なった場合は、会員バッジがある発言だけを修復します。非会員の顔文字にある `□` は残します。
会員が手で打った単独の `□` と削除済みスタンプの区別はできません。

### 採掘した札は、すべてそのチャンネル専用

自動で用意するスタートデッキは、**全札を `scope: "channel"` にします**。
別の部屋にも出てくることは、使う人が共通札として保存したいかどうかの答えにはなりません。
チャンネルごとの用字を保ち、共通札に寄せるための綴りの統一もしません。

`tools/scope.mjs` はこの出力を作ります。名前は従来のままですが、上位20件・他室2%による
`global` / `channel` 判定は行いません。既に選ばれた歌枠札を再び10枚に切ることもありません。

```
node tools/produce-presets.mjs --run chat-presets-YYYYMMDD --finish
```

`--finish` は保存済みの候補だけで再生成し、取り直しません。解析に使ったコードの記録は保ち、
出力には現在の「全札チャンネル専用」の方針を適用します。

**同梱するときは**、気に入ったデッキを書き出してから、

```
node tools/add-preset.mjs ~/Downloads/oshideck-preset-さくら.json
node tools/add-preset.mjs ~/Downloads/oshideck-preset-さくら.json --channel UC…
```

とすれば `presets/<チャンネルID>.json` として入り、`presets/index.json` に名前が載ります。
あとは commit するだけ。**同じチャンネルの組があれば
差し替えます** ── 名前ではありません。ひとつの空デッキに2組が出るのが困るのであって、
表示名が同じチャンネルが2つあっても一緒には出ないからです。
取り込む前に拡張機能自身の検証を通すので、**読み込み時に弾かれるものはリポジトリに入りません**。

**同梱するものは必ずチャンネルを名乗ります。** 配信の最初に何を言いたいかはその配信者のもので ──
合言葉も、掛け合いも、スタンプも ── どこでも通る挨拶の詰め合わせは、一度打てば済む話です。
メン限スタンプが入っていれば書き出しが勝手に名乗りますが、文字だけのデッキには名乗るものが
無いので、そのときは `--channel` で言います。

同梱の `presets/` には **2,671組・27,527枚** が入っています。うち2,590組は、2026-11-01 に固定した
Holodex の活動中2,914チャンネルから作ったものです。270には使えるチャットリプレイがなく、
54には規則を満たす札がありませんでした。旧版の390組はすべて新版に置き換わっています。

別途加えた1組は、Holodexに未収録の「むずちゃんねる」です。2026-11-12 にYouTubeの公開ライブ一覧から
歌枠2配信と通常13配信を取り、5,157件の文字コメントから10枚を選びました。分類は配信タイトルにある
「歌枠」などの表記に基づき、歌枠リレーやコラボと明記された歌枠、会員限定配信を除外しています。
割合・長さ・通常配信の補充規則は同じです。10枚ともチャンネル専用です。

<!-- additional-preset-research -->
公開回放の追加調査（2026-11-12）では、上記の活動中名簿に含まれないチャンネルや、前回は使える回放がなかったチャンネルも対象にしています。現在80組を追加済みです。Holodexに配信情報があればその分類を使い、未掲載ならYouTubeの公開ライブ一覧を最大150件調べ、タイトルから歌枠・明記されたコラボ・会員限定枠を区別します。歌枠2本・通常13本までという採用数と札の選択規則は同じです。使える回放や規則を満たす札がないチャンネルには、空のセットや代作の札を入れません。
<!-- end-additional-preset-research -->

読み込みは足し算です。**内容が完全に一致する共通札があれば、それを最優先で使います。**
共通札がなければ読み込み先のチャンネル専用札を再利用し、どちらもなければ新版の札を追加します。
保存順には左右されず、既にある札の範囲・ID・履歴は変えません。よそのチャンネル専用札は再利用せず、
似た反応でも用字やスタンプIDが違えば別の札として扱います。

ファイルからの読み込みも同じ規則です。ファイルに `global` と書かれていても、新たに作る札は
読み込み先のチャンネル専用にします。バックアップの復元は別で、保存していた範囲をそのまま戻します。
旧版から既に保存した札も、更新時に削除や範囲変更はしません。

読み込みはチャンネルの名前も一緒に覚えます。名前はふつう札を保存したときに分かるものなので、
スタートデッキで始めたデッキは編成ページにIDのまま並んでいました。

同梱のファイルはサービスワーカーが読みます。拡張機能自身のファイルであって、YouTubeのページに
見せる理由が無いからです（`web_accessible_resources` に出すと見えてしまいます）。

### 1チャンネル1ファイル

同梱のスタートデッキは `presets/<チャンネルID>.json` に1組ずつ置いて、`presets/index.json` が
どれがどのチャンネルのものかを言います。2,671組の index は278KB。ワーカーは起動時にこれを読み、
そのあと**目の前のチャンネルの1組（中央値3.5KB、最大20.1KB）だけ**を取りに行きます。
全セットのJSON本体は合計10.38MBですが、起動のたびに全部を読み込む構成にはしていません。
画像は同梱せず、スタンプのHTTPS画像URLを札に持たせています。

スタートデッキサーバー（[Roadmap](#roadmap)）はまだ設けていません。index と各セットの大きさを
計測した上で、配布方法を判断できます。

## Export and import

設定ページのいちばん下から、プール・デッキ・チャンネル設定・表示設定をまとめてJSONに
書き出せます。ファイル名は `oshideck-YYYY-MM-DD.json`。

読み込みには2つのモードがあります。

| | 何をするか | 使用回数 |
| --- | --- | --- |
| **追加** | ファイルの札を今のプールに足し、デッキへの所属も足す | 既存の札は自分の回数を維持、新しく来た札は0から |
| **全部置き換え** | 今のプールとデッキを捨ててファイルの内容にする | ファイルの回数をそのまま復元 |

**追加**では、札は**idではなく内容で照合します**。同じコメントを別の環境で保存すると
uuidが違うので、idで見ると同じ札が二重になってしまうためです。結果として、
同じファイルを2回読み込んでも何も増えません。

**全部置き換え**は1クリックでは実行されません。ファイルを選ぶと枚数を表示して止まり、
「置き換える」を押して初めて適用されます。

ファイルは適用前に検証します。壊れたJSON、札の形式違い、存在しない札を指しているデッキは
理由を出して拒否し、一部だけ適用されることはありません。

実装は `src/backup.js`（純粋関数）と、設定ページ側の配線です。

## Reporting a problem

Options → 診断ログ → ファイルに保存 exports a bounded timeline and the last observed states.
It covers channel detection, panel visibility/folding/filtering, card operations, draw decisions,
settings and colour sources, preset/file loading, send attempts, and unexpected extension errors.

```
2026-09-06 18:52:04  channel    video=Gv0g2GYipSM id=UCPb47… via=card-by-handle
2026-09-06 18:52:05  panel      reason=ready mode=hand shown=10 width=400
2026-09-06 18:52:06  operation  op=addCard card=c1 status=ok duplicate=true
2026-09-06 18:52:07  draw       reason=below-share min=6 share=0.3 messages=30 belowShare=1
2026-09-06 18:52:08  play       stage=send status=clicked
```

`clicked` means the extension clicked YouTube's send button; it does **not** confirm delivery.
`filled` and `timeout` are distinct. A rejected operation, a failed storage read and a failed
storage write also have separate reasons. An absent preset, an unreadable file and validation
refusal are separate events. Validation records only the message code, not its arguments.

The export includes the current settings/card-count snapshot and up to 64 last observations,
labelled by context/session (they may come from pages already closed). The timeline keeps the
newest 300 entries, merging adjacent repeats. Unchanged state observations are suppressed across
other event types; counters for an unchanged draw decision are sampled at most twice a minute.
A changed draw decision is recorded immediately. Draw counts are **messages**, not distinct viewers.

Only allowed fields are persisted or exported: numeric counts, validated channel/video ids,
fixed status codes and settings. Card ids are replaced by bounded, session-local aliases such as
`c1`, because a drawn card's internal id contains its wording. Card/chat text, viewer names,
user filenames, validation arguments and exception messages/stacks are excluded, including
when an old stored entry contains them. Error records keep only the type and extension code location.

Diagnostics write only `journal` and `journalState`, on a queue independent of card/settings writes.
A diagnostic write that fails or stalls cannot block the card queue or change an operation's reply.
Failed batches are bounded in worker memory, retried on the next write and included in exports;
that unpersisted buffer can be lost if the worker stops before storage recovers. Clearing the log
also clears the snapshots/buffer and resets observation suppression so reproduction can be logged again.

## Cards clip, never spill

札の中身は長さがまちまちです。スタンプ5個なら 110px 必要ですが、104pxの札に使える幅は
88pxしかありません。そのため中身の器は**折り返し・切り抜き・フェード**の3つを必ず持ちます。

- `flex-wrap: wrap` — フレックスの子は既定で折り返さないので、これがないとスタンプが
  一列のまま札の外へ押し出されます
- `overflow: hidden` を札そのものにも — 器から出たものを枠で止めます
- `max-width: 100%` と `min-width: 0` — フレックスの子は中身の幅で決まり、
  min-content より縮まないので、これがないと折り返さずに両端が切れます

### いっぱいとは何か

中身が入りきらなくなったら、札は**2段階で応えます**。まず一段小さくし、それでも足りなければ
もう一段小さくして、裾をフェードさせます（`data-length` = `medium` / `long`）。

ここで2つ間違えていました。

**ひとつめ。段はフォントサイズを変えるだけで、スタンプには届いていませんでした。**
`.od-emoji` がピクセル固定だったので、スタンプだけの札は段を踏んでも何も縮まず、3列目が
札の縁でただ切り落とされていました。いまは `1.6em` です ── 小サイズの12pxでちょうど従来の
19pxになり、そこから札のサイズにも段にも付いていきます。帯・一覧・編成ページは自分の高さが
あるので、それぞれ自分のpxを持ったままです。

**ふたつめ。入りきるかどうかは面積の話なのに、幅しか数えていませんでした。** スタンプは
幅が2文字ぶんですが、高さも1.5行ぶんあります。小サイズの札は文字なら8字入るところ、
スタンプは4個しか入りません。2と数えていたせいで段が遠すぎ ── 縮むのが10個目、フェードは
一度も来ませんでした ── 5個目で3列目が切れている横で、予算はまだ余っていると言っていました。
いまは3と数えます:

| 小サイズの札 | 入る数 | 段 |
| --- | --- | --- |
| 19.2px（そのまま） | 4個 | — |
| 14.4px | 6個 | `medium` |
| 11.2px ＋ フェード | 12個 | `long` |

文字のほうの段は動いていません。スタンプの数え方だけを直したので、`おはよう` が縮む条件は
以前と同じです。

### 同じものを何度も言っている札

そしてほとんどの札がそうです。チャットから掘った2609枚のうち**1150枚**が、絵の繰り返し
だけでできています ── スタンプ3つ、スタンプ5つ、`🦢✨` ×2。そのまま描くと小サイズの札は
5個を入れるために縮まねばならず、しかもその札はスタンプこそが中身です。

なので札のほうは**一度描いて数えます**（`🪽🫧🎶×2`）。小サイズで原寸のまま出せる札が
**48% から 85%** になります。

| 小サイズの札 | 原寸 | 一段 | 二段＋フェード |
| --- | --- | --- | --- |
| そのまま描く | 1250枚 | 1321枚 | 38枚 |
| ×N で描く | 2228枚 | 371枚 | 10枚 |

**繰り返されているものが、誰かが言ったものでなければなりません。** 絵は必ずそうです ──
同じスタンプがもう一度あるだけですから。文字はたいていそうではありません: `www` は単語
そのもの、`88888` は拍手、`てぇてぇ`・`よしよし`・`そうそう`・`ぎゅっぎゅっ` はどれも
「重ねること自体が語」です。`×N` と書くと語が割れます。

**分け目は終止符です。** `はい！はい！はい！はい！` はひとつの発話を4回言ったもので、
`はい！×4` とぴったり読めます ── `アンコール！×2`、`安心！×3`、`ちーよみ！×2` も同じ。
掘った中の「文字の繰り返し」354枚で、この線はきれいに通ります:

| | 枚数 | 例 |
| --- | --- | --- |
| 終止符がある → 数える | 14枚 | `はい！` `アンコール！` `安心！` `ちーよみ！` `サーターン！` |
| 無い → そのまま | 340枚 | `おお`151 `www`83 `ｗｗｗ`67 `GG`9 `うんうん`6 `ほうほう`5 … |

単位は2原子以上でなければなりません。`！！！！` の `！` は「言ったもの」ではなく
`www` と同じ側だからです。

**単位は最短のものを取ります。** スタンプ6個は「3個を2回」ではなく ×6 です ── どちらも
札を言い当ててはいますが、札なのは片方だけです。

そして**帯は省略しません**。札は読めるように縮め、帯は送られるものをそのまま出す ──
カーソルを置けば、`×5` が実際には何になるのかがその場で分かります。

## Nothing floats over the chat

パネルはチャットのいちばん下に置かれるので、その上に浮くものは何であれチャット本文を隠します。
そこで、浮かせる代わりに**パネル上部の帯を使い回します**。帯は状況に応じて顔を変えます。

| 状況 | 帯の中身 |
| --- | --- |
| 通常 | チャンネル名 ＋ 共通 ＋ 枚数 |
| 入力欄に何かある | 保存先の2ボタン |
| 札を編集中 | 「編集中」＋ ［更新］［やめる］ |
| プールを開いている | ［手持ち N］［スタートデッキ N］の切り替え |
| 札やボタンにカーソル | 札なら中身そのもの、ボタンならその説明（`setPeek`） |
| 保存・削除・移動の直後 | 通知と「元に戻す」（`showToast`） |

右端はいつも操作です ── 「編成」、プールに札があれば「プール12」、プールを開いていれば
「閉じる」。**プールへの入口はもともと手札の下の横幅いっぱいのボタンでした**が、短いことを
ひとつ言うために1行を使っていました。帯はもともと「ほかに置けば場所を取るもの」の置き場
なので、そちらへ移しています。帯の操作は縮みません（`flex-shrink: 0`）── 譲るのは
チャンネル名のほうで、そちらには省略記号があります。

そのため、配信ページ側のUIに浮遊トーストはありません。読み上げ用の名前は `aria-label` で
別に付けています。

`title` が残っているのは**4か所だけ**です ── 引いた札の ＋ と保存先の2ボタン、そして
その2つが押せないときの理由。どれもブラウザ標準のツールチップで、帯が同じことを言えない
場面（押せないボタンにはカーソルの説明が出ません）に限っています。

**断られたことは、押した札の上に出します。** 帯は隅にあり、見る理由がありません ── そして
押して何も起きなかったときは、帯だけが「なぜ」を持っていました。押した札はカーソルの下に
あるので、そこで赤く震えます（動きを減らす設定なら色だけ）。帯の文はそのまま、ただし
唯一の知らせではなくなりました。

**起きたことは、起きたところが語ります。** 「札を更新しました」は札の中身がその場で変わり、
「編集をやめました」は入力欄が空になり、「◯◯を入れました」は10枚の札が現れます ── どれも
隅で言い直す必要がありません。消さなかったのは次の3つだけです:

- **「元に戻す」が付いているもの**（デッキから外した・削除した）── 取り消す入口がそこにしか無い
- **「同じ札がもうあります」**── 手札に新しい札は増えず、既にあった札が光るだけなので、
  見逃すと保存に失敗したように見えます
- **保存先の報告**（共通／このチャンネル専用）── 違いは札の上端の細い色帯だけで、
  それが何を意味するかを先に知っている必要があります

**知らせは、次に何かした瞬間に消えます。** 帯は1行しかないので、通知は保存先のボタンと同じ
場所を取り合います ── 打った内容についてのエラーが、それを直して押し直すためのボタンを
6秒間隠していました。起きたことの報告は、次のことが起きた時点でもう報告ではありません。

同じ理由で、札を編集し始めたときの「直したら『更新』を押してください」は**やめました**。
帯はそのあとすぐ「編集中 ［更新］［やめる］」になります ── 同じ文を、押せるボタンで言って
いるのに、文のほうがボタンを隠していました。

**札にカーソルを置くと、帯はその札を出します ── 文字ではなく、絵で。** 札は小さく、入りきら
なければ縮んで消えていくので、帯のほうが場所があります。

これは一度やめて、戻した機能です。やめた理由は正しかったのですが、もう当てはまりません ──
当時の帯は札を**文字にしか**できず、メンバー絵文字の文字はYouTubeがそれを整理している名前
なので、`:_tadaima:` ×3 が `tadaimatadaimatadaima` と読み上がっていました。いまは帯も絵を
描くので（[Standard emoji](#standard-emoji) と同じ `toFragment(…, { preview: true })`）、
出るのは札に出ているものそのものです。

**ただし、札が自分について語っていることは言いません。** いま言われている札は隅で呼吸して
いるので、5人か50人かですることは変わりません ── 変えるのは点のほうです。引いた札に
「＋で保存」と教えるのも同じで、その ＋ は札の上の、ほかの札と同じ場所にあります。
鍵のかかった札だけは例外で、そこは帯にしか言えることがないので**言葉**になります。

**YouTube自身のツールチップを呼び出さないこと。** `shared-tooltip-text` はYouTubeの属性で、
読むのは `tp-yt-paper-tooltip` です ── `collectTokens` がその要素を除外しているのは、
まさにそれがこの木の中に現れるからでした。パネルはライブチャットのレンダラの中に間借りして
いるので、札の面にこの属性が付いていると、カーソルを置いた瞬間にYouTubeが `:_ただいま:` を
チャットの上に浮かせます。この属性が要るのは**入力欄に入れる側だけ**で ── そこから読み戻した
ときに、メンバーが要るかどうかを言える唯一の手がかりだからです ── 札の面は読み戻されないので
付けません。

逆に、**YouTube 自身がその場所を使いに来ることもあります**。スーパーチャットを開くと、YouTube は
入力欄を消さずに畳んで、同じ隅に自分のパネルを出します。畳まれた要素も `querySelector` には
答えるので、「見つかった」を「使える」と読んでいたパネルは、そのまま SC パネルの上に描き続けて
いました。いまは**描かれているか**（`getClientRects()`）で判断し、畳まれていれば身を引きます。

合図は入力欄レンダラの属性変化だけを見ます（今日の YouTube では `product-picker-open`）。
属性名は書いていません ── 名前が変わっても「もう一度見ろ」は届き、判断そのものは測って行うので
壊れません。チャットのメッセージごとに走る経路では測りません。レイアウトを強制するからです。

## Taking someone else's comment

チャット欄のコメントにカーソルを置くと、右端に ＋ が出ます。押すと**その場で**保存先の2つが
現れます ── チャンネルの色の丸と、灰色の丸。押したほうに保存され、プールとデッキの両方に入ります。
メン限スタンプ入りなら灰色は押せません。

**選択肢は押した場所に出ます。** 最初はパネル上端の帯に出していましたが、帯はチャットの ＋ から
遠く、設定ページの下端に警告を書いていたのと同じ間違いでした。

言うほうがしたいときは **⇧＋クリック**で入力欄に入ります（札を ⇧＋クリックすると送信になるのと
同じ ⇧ です）。判断も重複の扱いも既存の保存経路がそのまま担当するので、この機能が持っているのは
「どこから中身を取るか」だけです。

読み取りは `tokens.collectTokens(message)` ── チャット連動の並び替えが以前から使っているものと
同じ呼び出しです。コメントと下書きは形が同じ（文字の中に `<img data-emoji-id>`）なので、
新しい解析は要りません。

ボタンはYouTube自身が各行の右に空けている32pxのガター（絶対配置・ホバーまで不可視）のすぐ内側に
入ります。**カーソルのある1行にしか存在しません** ── DOMに置くボタンは常に1つで、行から行へ
移るだけです。絶対配置なので本文は詰まらず、1行ごとにボタンを撒く必要もありません。

## Drawing a card from the chat

チャットが**バーストしたとき**だけ、持っていない反応を1枚、手札の左端に差し込みます。
麻雀でツモるのと同じで、打ってもいいし、手札に入れてもいい。

### 誰かが喋っている行だけ数えます

チャット欄の行が全部コメントとは限りません。**メンバーシップギフト**は受け取った人の
数だけお知らせを出します ──「@ようかん-MP さんからメンバーシップを受け取りました」 ──
50人分なら数秒で50行、しかも**贈り主が同じなので全部まったく同じ文**です。
`src/trending.js` の持っている物差しはどれもこれを「波」と読むので、パネルはその
お知らせを札として差し出していました。新規メンバー行、スーパーステッカー、YouTube
自身のお知らせも同じです。

**文面ではなく要素で見ます。** 文面はYouTubeのもので、見ている人の言語で変わります
── 文のリストを持つなら YouTube の全言語ぶん必要で、しかも向こうが言い回しを変えた
翌日には間違いになります。**どの種類の行かは変わりません**。誰が見ていても同じ
カスタム要素です。

なので**許可リスト**にしました。中身が「誰かが打った言葉」である2種類だけを通し、
残りは何なのかを知らないまま素通りさせます ── 知らなくていいことが、この方式の
いちばんの取り柄です。

```
yt-live-chat-text-message-renderer    通常のコメント
yt-live-chat-paid-message-renderer    スーパーチャット（誰かが打った言葉です）
```

`＋`（他人のコメントを取る）が前から使っていた2種類と同じものです。だから規則は
`src/trending.js` に一つだけ置き、`content.js` はそれを読みます。

絵文字のURLだけは**どの行からでも**拾います。ギフトのお知らせに入っているメン限
スタンプも同じ場所にある同じ絵で、拾っているのはURLだけだからです ── なので収穫は
行をはじく**前**にやります。

ラッパーに包まれていても同じコメントとして扱います。YouTubeは以前これを入れ子に
したことがあり、厳密に読むと**静かに**何も反応しなくなります（空のランキングは、
静かなチャットと見分けがつきません）。

**保留**: メンバーシップのマイルストーン（`yt-live-chat-membership-item-renderer`）には
本人が打ったコメントが入ることがあり、いまの許可リストはそれも落としています。入れて
よいかは「新規メンバーになりました」だけの行に `#message` があるかどうか次第で ──
あれば、同じ問題を別の行で開け直すことになります。**実ページで未確認**。間接的な証拠
（他拡張の実装、YouTube.js のパーサ）は `#header-subtext` に文言があり `#message` は
無いか空、という方向ですが、確証はありません。

```
● 稀羽すう    14枚                      [編成]

  ┊888┊    ╭──╮╭──╮╭──╮╭──╮╭──╮╭──╮╭──╮
  ┊   ┊    │札││札││札││札││札││札││札│
   ↑ 引いた札（破線・扇の外・呼吸する縁・すこし離して）
```

**重なりは左が上です。** 兄弟要素は後のものが上に描かれるので、放っておくと右端の札がいちばん上、
左端 ── **いちばん使う札**が、いちばん下に埋もれます。手札は大事な順に並んでいるのだから、
重なりもそう並べます。引いた札の光が隣に切られていたのも、同じ順番のせいでした。

**左端は「手札の左端」ではなく、独立した場所です。** 手札が空のときは左端にする手札が無いので、
引いた札が真ん中に出てしまっていました。いまは引いた札が自分の区画を左端に持ち、手札は残りの幅で
中央に扇を作ります。

**行を増やしません。** パネルはチャットのいちばん下にあるので、行が増えればその分チャットが狭く
なります。代わりに手札が重なりを詰めて場所を空けます ── 400pxのサイドバーで小サイズなら、
7枚の重なりが8pxから17pxになって1枚ぶんが生まれる、という程度です。詰めきれない幅のときは
引きません。

**いつ出るか、どれだけ残るか、どれだけ速く忘れるかは、設定で変えられます。** 部屋の賑やかさは
チャンネルごとに違いすぎて、こちらで決め切れる数字ではないからです。

| 設定 | 左 | まんなか | 右 |
| --- | --- | --- | --- |
| 引きやすさ | ひかえめ 8回・4割 | **ふつう 6回・3割** | よく引く 4回・2割 |
| 残る時間 | **ながめ** 60秒 | **ふつう 30秒** | みじかめ 15秒 |
| 反応の速さ（半減期） | ゆっくり 30秒 | **ふつう 20秒** | はやい 10秒 |

落ち着いているほうが左です。残る時間だけ長いほうが左に来るので、3行とも同じ向きに
読めます。

残る時間と反応の速さは、段のかわりに**秒数を直接書くこともできます**（下記「段と、秒」）。

設定ページでは、この3つは**それが効くところに置いてあります** ── 引きやすさと残る時間は
「チャットから引く」の節、反応の速さは並び順のすぐ下。どれも一度は「手札の並べ方」に
まとめて置いていましたが、そこは札の大きさと行数の場所で、**同じ節にあるというだけで
関係があるように読めてしまいます**。

**数字ではなく段で出しているのは、独立していないからです。** 何回言われたかと、部屋のどれだけを
占めたかは、二つで一つの「波」を決めています。別々に触れるようにすると「2回で5割」のような、
意味をなさない組み合わせが作れてしまいます。設定ページの説明には、その段が実際にいくつなのかを
そのまま書いてあります ── `ふつう` という名前は、それが何をするのか誰にも教えないので。

値は `src/store.js` の `TUNING` に全部あります。段の意味を変えるのは一行です。

**いつ出るか（既定）。** 12秒のあいだに**6回以上**、かつ**その間に流れた発言の3割以上**（割合の分母は
発言の時刻だけを別に数えています ── 文面を覚えておく数には上限があり、その上限が分母を兼ねていた
ころは、速いチャットで「部屋の3割」が実際より大きく見えていました）。二つ要るのは、
どちらか片方では意味をなさないからです ── 回数だけではチャットの勢いが分からず、「4回」は静かな
部屋では波でも賑やかな部屋ではただの雑談で、実際それで誰も乗っていない言葉が出ていました。
割合だけなら、ほとんど無言の部屋で最初の2発言が100%になってしまいます。本物の波では、みんなが
他のことを言うのをやめます ── それを見ています。

波の回数は文面ごとに数えますが、デッキに同じ反応があるかの判定では、札の表示と同じ繰り返し単位を使います。
👏×5を持っていれば👏×6は引かず、回数違いの札をデッキに加えた場合も表示中の抽札を終了します。
保存内容や送信時の回数は変えません。`きちゃ` と `きちゃきちゃ` のような普通の言葉は完全一致のままです。

**出たあとは30秒とどまります**（期限が来たら自分で描き直しに行きます ── 期限に気づくのは描き直しの
ときだけなので、チャットが静まると誰も気づかないまま居座っていました）。 毎回引き直すと反応から反応へちらつき、カーソルの下で入れ替わる
札は無いよりたちが悪いからです。デッキに入れた時点でその札の役目は終わります。

**とどまるあいだ、描き直しもしません。** チャット連動は数秒ごとに描き直しますが、描き直せば要素は
新しくなり、新しい要素はアニメーションをやり直す ── 引いた札が数秒おきに左から滑り込み直して、
跳ねているように見えていました。いまは「パネルが映しているもの」に変化が無ければ描き直しません。
チャットの回数が増えただけ、は変化に数えません（札が光り始めた／やんだ、は数えます）。それでも
何かの都合で描き直しになったときのために、滑り込みは本当に新しい札のときだけで、光は前の続きから
始まります。

**打つか、取っておくか。** 札を押すと入力欄に入り、そのまま送れば打ったことになります。取って
おくときは札の **＋** を押すと、その場に保存先の2つが出ます ── 送信を経由しないので、「札を
クリックしたら自動で送信する」を入れていても使えます。⇧＋クリックなら保存せず入力欄にだけ
入ります。

出さないもの:

- すでに手札にある反応（放っておいてもチャット連動で前に出ます）
- 送れないメン限スタンプ ── 別チャンネルのもの、そしてこのチャンネルのものでもメンバーでない
  あいだ。押して失敗する札は、無いほうがましです。**メンバーであれば出します**（[Member
  emoji](#member-emoji)）── 引いたあとメンバーでなくなれば、その場で引っ込めます

設定の「チャットから引く」で止められます。

### 段と、秒

「引いた札が残る時間」と「反応の速さ」は段で選びますが、**秒数を直接書くこともできます**。
段のほうが既定として正直です ── あれは測った値ではなく手触りの判断なので ── が、自分の
配信のチャットを長く見てきた人は、こちらが用意できるどの数字よりいい数字を持っています。

| | 左 | まんなか | 右 |
| --- | --- | --- | --- |
| 引いた札が残る時間 | 60秒 | **30秒** | 15秒 |
| 反応の速さ | 30秒 | **20秒** | 10秒 |

長いほうを左に置いています ── 左ほど落ち着いていて、右ほど目まぐるしい。

**「引きやすさ」には秒の欄がありません。** あれは2つの数（何件と、部屋の何割）が互いに
噛み合って初めて意味を持つもので、ばらばらに決められるようにすると「2件で半分」のような
意味のない組み合わせを招きます。

秒は**書き込む時点で確定させます**（`cleanSettings`）。空欄は `NaN` として届きますし、
用意していない段の名前が入ってくると、読むたびに黙ってまんなかの段になってしまいます ──
1秒から10分の間に収め、読めない値はその場で断ります。

## Chat-driven sort

「チャット連動」は、いま多い反応に合う札を前に出します。数えるだけでなく、**新しさで重みを付けます** ──
1件は `2^(-経過/半減期)` ぶんで、半減期は既定で20秒（「反応の速さ」で変えられます）。
**捨てるのは半減期の4.5倍より古いもの**（既定で90秒、ただし最低でもバースト窓の12秒）で、
その時点で重みは4%ほどなので、窓から落ちること自体は見えません。半減期を10分にしても
固定の90秒で切られる、ということにならないように、窓のほうが付いていきます。

比較は正規化した署名どうしで行うので、書き方の揺れは吸収されます。

| チャット | 手札の札 | 一致 |
| --- | --- | --- |
| `88888888888` | `888` | ○ |
| `はい！はい！はい！はい！` | `はいはい` | ○ |
| メン限スタンプ ×4 | 同じスタンプ ×1 | ○ |
| `わこつ〜` | `わこつ！！！` | ○ |
| `おつ` | `888` | × |

**なぜ重みを付けるのか。** 平らに数えていたころは、大量の拍手のあと次の曲が始まっても拍手が先頭に
居座りました ── 窓の中の1件はどれも同じ重さで、端から落ちる瞬間まで満額だったからです。いまは
80秒前の拍手40件は2.5点なので、新しい反応が3件で追い越します。しかも落ち方が滑らかなので、
窓から抜けた瞬間に順番が跳ねることもありません。

- 並べ替えは4秒に1回まで。カーソルが札の上にある間は動きません（配信中に札が指の下で入れ替わるのを防ぐため）
- 帯に出る「いまチャットで◯回」は素の件数です。順番を決めるのは重み、見せるのは件数
- 同じ重みの札は、編成ページで決めた順に並びます。チャットの重みが無いときもその順を使い、使用履歴へ切り替えません
- 実装は `src/trending.js`。署名は「連続の繰り返し」と「全体の繰り返し」を1回分まで畳んで作ります

## 言語

日本語・繁体字中国語・英語。**設定ページで選べます** ── `chrome.i18n` はブラウザの言語に従うだけで
中から切り替えられず、それはここでは逆に困ります（日本語の配信を、中国語のChromeで見ている人が
どちらを選ぶかは、その人しか知りません）。選んでいなければブラウザに合わせます。

言葉は `src/i18n.js` の表に全部あります。**日本語が原文**で、訳の無いものは日本語のまま出ます ──
鍵の名前（`bar.global`）よりは、読めない言語の文であるほうがまだ文だからです。逆に**存在しない鍵**は
鍵の名前がそのまま出ます。そちらはバグで、出ていれば気づけます。

- 画面側は `data-i18n="鍵"`（属性なら `data-i18n-placeholder` など）。中に残してある日本語は
  スクリプトが動く前に出る控えで、空のページよりはましという役割です
- `$1` `$2` は呼ぶ側が順に埋めます。名前ではなく番号なのは、語順が言語で変わっても
  番号のほうは動かないからです
- `tools/check-i18n.mjs` が、**コードに直に書かれた日本語**・存在しない鍵・誰も使っていない鍵・
  原文と `$1` の数が合わない訳を全部出します。翻訳は「95%終わった」状態が長いので、
  残りを人が数えないで済むようにしてあります

英語は日本語より長くなります。帯の中で**縮まないボタン**（「Anywhere」「Pool 12」「Build」
「Close」）は短い語を選んであり、チャンネル名のボタンだけが縮んで `…` になります
（`.od-save-channel` の `flex-shrink: 1`）。

通知のほうは縮みません。`.od-notice-text` は `nowrap` と `text-overflow: ellipsis` なので、
長い通知は折り返されずに**文の途中で切られます**。日本語は十数文字で言えていて一度も届かず、
英語は7件が端を越えていました ── 見るには400pxのサイドバーを配信中に開くしかなく、誰も見て
いませんでした。

なので測ります。`tools/check-width.mjs` が Helvetica/Arial の字幅（1/1000em）で英語の文言を
全部測り、帯に残る幅と比べます。字幅表は実物のChromiumが実物のCSSで出した5つの値と0.1px以内で
一致しています。測るのは英語だけ。表にCJKの字幅は無く、**知らない文字は推測せずに失敗**します。

**残る幅は計算します。** 測定値は `BAR = 376`（400pxのサイドバーから `#oshideck-root` の
左右12pxを引いたもの）だけで、そこから帯を分け合うボタンの幅を引きます ── `プール99+` と
`編成`。定数として **238.2px** と書いていたのをやめたのは、ボタンが変われば黙って古くなるからで、
実際に古くなりました（`プール10000`）。いまは `プール24` と `編成` を渡すと **ぴったり238.2px**
が出ます ── Chromiumがまさにその帯で測った値で、その一致はテストが見張っています。

**何が出るのかは呼び出しから読みます。** `showToast(t("..."))` だけでなく：

- 帯が自分で言う一行（`barLine`）── 通知は数秒、これは札が入るまでずっとそこにいます
- **名前で渡された文**（`showToast(saved)`）── `saved.*` は全部この形で、ひとつも測られて
  いませんでした。名前の束縛を一段だけ辿ります
- `$1` に**別の文言が入る**場合（`toast.saveFailedKept` は文ごと渡されます）── チャンネル名を
  代入していたせいで90px過小評価していました
- そして**どれが出るのか読めなかった呼び出しは失敗**にします。黙って飛ばすのは、成功に
  見える失敗です

**訊いている問いを変えました。**「文言が見つかったか」ではなく「**この式が出しうるものを全部
説明できたか**」です。前者だと `ok ? t("toast.deleted") : other` は書き下してあるほうの枝が
見つかった時点で「分かった」になり、より広いかもしれない `other` は一度も見られないまま
「全部収まります」と報告されます。二回の review が続けて見つけたのは、全部この形でした。

読む文法は**閉じて**います ── `t("…")` の呼び出し、裸の名前、そしてその二つの三項・`||`・`??`。
それ以外（テンプレート文字列、他の関数の呼び出し、プロパティ参照、手で組み立てた文字列）は
**読まずに拒否**します。読めなかった呼び出しは失敗で、失敗は人が見ます。

名前を読むのは、ファイルが**迷う余地を残していないとき**だけです。その判定は
**数えること**であって、形を**並べること**ではありません:

- `const <名前> =` がある
- そして、ファイル中のその名前の出現が**全部すでに読んだもの**か ── その `const` 自身か、
  いま読んでいる呼び出し（`t(…)` / `showToast(…)` / `barLine(…)`）の括弧の中か
- その中身をこの同じ文法で読める

ひとつでも説明のつかない出現があれば、その名前は読みません。

**なぜ数えるのか。** 三周のあいだ、ここは「この名前は引数か？」を訊いていました。それに
答えるには引数の**形を並べる**しかなく、並べたリストは終わりません。`function f(x)`、
`(x) =>`、`x =>` までは並べていて ── オブジェクトのメソッド `go(x) {}`、クラスのメソッド、
`catch (x)`、`for (const x of …)` は素通りし、**他人の文**を答えていました（自分で試して
確認しました）。数えるほうには、欠けうるリストがありません。

それ以前の三つの読み方も全部「その名前の値ではないもの」を答えていました ── ファイル全体
から適当な束縛、インデントから推測した関数スコープ、同名のプロパティ。そのうち一つは、
無関係なプロパティのほうが広いせいで**収まる文言を失敗させる**ことまでできました。

**コメントは先に空白にします**（オフセットは1文字=1文字で保たれます）。コメントアウトされた
`showToast(t("…"))` は通知ではありませんし、文章の中で名前に触れているのはその名前の
使用ではありません。

だから `content.js` 側も**文を引数で渡さない**ように直しました（`kept: t("toast.inputKept")`
→ `keeping: true`、文は呼び出しの場所に書く）。帯でいちばん広い一行がそれなので、測れない
ままにしておく価値がありません。

`$1` は別の問いです。名前はこのファイルで文を持ち回る形なので、**読めない名前は失敗**
（チャンネル名を代入していたせいで90px過小評価していました）。プロパティや個数など
**そもそも文言ではないもの**は値なので、代入見本を使います。

同じ `key` が**二か所から**出るなら二か所とも測ります（`toast.saveFailedKept` がそうです）。
最初の一件だけ覚えていたので、広いほうの引数を渡している呼び出しが丸ごと測られていませんでした。
`$1` に入る候補が**ひとつでも測れなければ失敗**です。`?? 0` にしていたので、測れない候補は
幅ゼロとして「いちばん広い」選考に負け、知らない文字も報告されませんでした。

## 推し色

デッキごとの色。**代表色とOSの選色器で選んだ色はHEXをそのまま保存**し、明度・彩度も保ちます。
色点とカードの色帯にはその色を使い、低彩度色の細い輪郭で黒・白も見分けられるようにします。
操作中の枠や光は読みやすいパレット配色を使い、低彩度色では無彩色になります。

- **8色の丸と色相スライダー** ── 明度・彩度を固定した色相配色を手早く選びます。
  選び直すと、それまでのHEX指定を外して新しい色相を保存します
- **現在の色の丸（`input[type=color]`）** ── OSのカラーパネルが開きます。
  カラーコード・スポイト・明暗・彩度を含め、選んだHEXを保持します
- **チャンネルの初期色に戻す** ── 保存した色相とHEX指定を外し、現在の代表色へ戻します。
  古い自動色を使っているデッキもこの操作で更新できます

**確認済みの入力。** 復元したv52の `selected_hex` 807件を優先カタログ `OSHI_COLORS` に保持します。
出典と選定状態は `tools/data/channel-colours-v52.json`、元CSVのSHA-256も同じファイルに残します。
807件すべてが公式に確認された色という意味ではなく、確認状況と利用者による選色の変更を記録しています。
彩雲ののの初期色は微灰白 `#F1F2F4`。保存済みの色指定は優先され、初期色へ戻す操作で新しい色に戻せます。
734件が現在の同梱チャンネルに対応し、残り73件もチャンネルIDで初期色を使えます。
`node tools/sync-colours.mjs` は入力と実行コードの一致を検査し、`--write` でカタログ部分だけを再生成します。
CSVの `selected_hue` は使いません。

v52に選定済みHEXが無いチャンネルには、従来のv53／追加表から取り込んだ色相・中性色を使います。
v53／extraのCSV原本は削除済みですが、v52由来の選色と出典は今後このJSONから再生成できます。
色が未定ならIDから決まる自動色を使います。実行時にCSVや調査用JSONは読み込みません。

既に `channelMeta` に保存した色があれば優先します。以前の版が自動保存した色相と本人が選んだ色相は
区別できないため、自動では上書きしません。初期色へ戻すボタンで明示的に更新できます。
完全なHEXは `channelMeta[id].color`、クイック選色の色相は `.hue` に保存し、バックアップにも含めます。
名前だけの更新やスタートデッキの追加でHEXを失わないようにします。

虹深°ぬふの色点は髪飾りを模した小さな選色器です。外周は12時が黄、時計回りに緑・青・藍・紫・赤・橙。
保存されたOKLCHの角度をそのまま使わず、表示色のRGB色相に換算してハートの位置を合わせます。
中央の四角は回転させず、ハートの先は常に中心へ向けます。チャットと編成ページで同じ部品を使います。

sRGBの外に出る色相は、チャンネルを切り詰めるのではなく**彩度を落として**戻します。切り詰めると
色相が最大9度ずれてしまい、ずれるのはまさに選んでいる当のものだからです。

## Member emoji

メン限スタンプは、それを配っているチャンネルでしか送れません。OshiDeckは `data-emoji-id` の
チャンネルID接頭辞から持ち主を判定し、別の配信では札を薄く表示してクリックを止めます。

**ただし接頭辞があること自体は「メンバー限定」ではありません。** YouTubeは誰でも使える絵文字を
配っていて（`:shelterin:`・`:face-red-heart-shape:` など）、それにもチャンネル接頭辞が付いています ──
配信者ではなく、ただの視聴者アカウントのものです。接頭辞だけを見ていたころは、**誰でも送れる札を
どこでも永久にロックしていました**。

見分けるのは**ショートカット**です。メン限は `:_名前:`、無料のものはアンダースコアがありません。
読む場所が2か所あって、しかも食い違うのが罠でした:

| | 配信ページのDOM | チャットの書き出し（yt-dlp） |
| --- | --- | --- |
| 表示名 | `alt="ぺここ"` | `accessibility.label` |
| ショートカット | `shared-tooltip-text=":_ぺここ:"` | `shortcuts: [":_ぺここ:"]` |

`alt` は表示名なので、そちらを見ているとアンダースコアはどこにも無く、**すべてのメン限スタンプが
解除されて**しまいます。ホバーしなくても `shared-tooltip-text` は読めます（実測）。

ショートカットを集めるようになる前に保存した札には、答えようがありません。その場合は
**メンバーが要る側に倒します** ── 逆に倒すと「押せるのに送れない札」になり、それはロックが
防ごうとしているものそのものだからです。

**メンバーかどうかも見ます。** 配っているチャンネルにいても、メンバーでなければ送れないので、
そこも同じように止めます ── ただし理由が違うので、言うことも違います。「別チャンネルのスタンプ」は
どうにもなりませんが、「メンバー限定」はメンバーになれば使えます。

判定に使うのは、**入力欄の横にある自分のバッジ**です:

```
yt-live-chat-message-input-renderer          ← パネルが間借りしているのと同じ要素
  #input-container > yt-live-chat-author-chip   ← 「自分」の身分
    span#chat-badges
      yt-live-chat-author-badge-renderer[type="member"]
```

実測して分かった、間違えやすいところが3つあります:

- **範囲を絞らないと必ず誤判定します。** メンバーがいないチャンネルなど無いので、文書全体を
  探せばバッジは必ず見つかります ── 入っていない配信で数えたら**57個**ありました。全部他人のです
- **`hidden` は答えではありません。** 別窓のチャットでは、メンバーであってもチップに `hidden` が
  付いています。バッジがあるかどうかだけが答えです
- **HTMLの中に会員フラグはありません。** `isSponsor`・`loyaltyBadges`・`sponsorOnly` ──
  どれも存在しません。DOMを見る以外に道がありません

答えは3つあります。**はい・いいえ・まだ分からない**。チップそのものが無いときは「まだ」で、
そのときは何も止めません ── 間違った鍵は、送れない札より始末が悪いからです。チャットを読み込み
直して測ったところ、**入力欄とバッジは同じ描画で現れます**（ずれ0ms）。パネルが立ち上がれる時点で、
答えはもう出ています。

**押すときにもう一度訊きます。** カーソルが札の上にある間、手札はわざと固まります ── 指の下で
入れ替わらないように ── ので、その間にメンバーが切れても鍵は古いままです。引いた札にいたっては
そもそも鍵がありません（誰のデッキにも入っていないので）。だから最後に効くのは押した瞬間の答えです。
古い鍵が効くのは**ページが答えられないときだけ**で、答えられるならそちらが勝ちます ── そうでないと、
固まっているあいだにメンバーに戻った札が、いつまでも断られ続けます。

**送るのは札ではなく入力欄です。** 札への ⇧＋クリックはその場で送ります。送らずに置くだけなのは
**引いた札の ＋** への ⇧＋クリックのほうで、送れないスタンプが
そこに残ったまま次の札を押すと、まとめて出ていってしまいます。だから送る直前に見るのは、
押した札ではなく**入力欄の中身**です。

**鍵のかかった札は、並び順が何であっても最後に回します。** デッキからは外しません ── メンバーに
戻れば元の位置に帰ってきます ── が、押せない札が手札の途中にあると、次に送るものを探している目が
ちょうどそこで止まります。

**まだできないこと。** バッジが言うのは**年数**（「メンバー（2年）」）であって、**等級**ではありません。
上の等級にしか配られないスタンプがあるチャンネルでは、「メンバーかどうか」までしか答えられません。

保存済みのCDN URLは古くなることがあるので、チャットに流れてきたスタンプの `src` を随時
拾い直し、描画時はそちらを優先します（`src/tokens.js` の `harvestEmoji` / `freshSrc`）。

## Standard emoji

`👏` や `🦢✨` のような普通の絵文字を、YouTubeはシステムフォントで描いていません。Live Chatは
**全部Googleの画像に差し替えます**。だから同じ一言が、チャットでは1つの絵、その隣の札では別の絵に
なります ── Windowsなら Segoe UI Emoji で3つめの絵です。札とは「これから送る一言の絵」なので、
**チャットと同じ画像を使います**。

**札の上だけです。** トークンとしては `text` のままで、入力欄に入るのも文字のままです。そこで絵に
するのはYouTube自身のレンダラーであって、代わりに `<img>` を置いても解決すべき emoji id がありません。
境目は `toFragment` の引数そのものです:

```js
toFragment(tokens, { preview: true })   // 札 ── 画像
toFragment(tokens)                      // 入力欄 ── 文字
```

**画像のURLは保存しません。文字から出ます。** 1配信分のチャット書き出しで数えた標準絵文字115種は、
115種ともYouTubeが実際に返していたURLと一致しました:

```
https://fonts.gstatic.com/s/e/notoemoji/15.1/<コードポイント>/72.png
```

落とし穴が4つあって、全部URLを叩いて確かめました:

- **コードポイントではなく書記素で切ります。** `👏🏻` は手＋肌の色、`😵‍💫` は顔2つ＋結合子、
  `👨‍👩‍👧` は人3人＋結合子2つ。どれも**1枚の絵**です。`Intl.Segmenter` が全部正しく切ります
- **`Extended_Pictographic` だけでは足りません。** 旗（`🇯🇵`）の中身は文字2つ、キーキャップ
  （`1️⃣`）の中身は数字なので、どちらも「絵文字ではない」と答えます
- **4桁に0埋めします。** `1️⃣` の `1` はコードポイント `31` ですが、ファイルは `0031_20e3` です。
  `31_fe0f_20e3` は404
- **異体字セレクタ（`FE0F`）は落とします。** YouTube自身が自分の emoji id から落としていますし、
  ファイルは付けても付けなくても返ります。ただし `2764_fe0f` は存在して `1f44f_fe0f` は404なので、
  残したままだと**半分は動いてしまい**、バグが運に見えます

絵が無い書記素（`™`・`♻` など）は404で返ってくるので、`error` で文字に戻します ── それが
この変更の前に札が見せていたものです。

**札の幅も同じ数え方にします。** 絵文字を文字として数えると `🦢✨🦢✨🦢✨` は9幅になり
（`✨` は1 UTF-16単位、`🦢` は2）、同じ6枚の絵が別の長さとして薄くなります。`splitEmoji` は
札の描画と幅の計測の両方が使う、ひとつの答えです。

## Icons

2枚の絵で4サイズを作ります（`tools/make-icons.sh`）。

| サイズ | 絵 | どこに出るか |
| --- | --- | --- |
| 16・32 | 札1枚 | ツールバー |
| 48・128 | 扇（札3枚） | 拡張機能の一覧、インストール時、ストア |

扇はパネルそのものの形で、これが何なのかを一番よく言い表します ── ただし**16pxでは潰れます**。

受け取れるのは、まさにこのためです。

行は「1行目を上限まで詰める」のではなく2行に均等割りするので、札が8枚しかないときに `7 + 1` とぶら下がらず `4 + 4` に揃います。

### ローカルの作業データ

配布に必要なファイルは `tools/build-release.mjs` の許可リストと `presets/index.json` で決まります。
配布対象でなくても、設計の原本と開発・検証用のツールは残しています。
完了済みの採掘データ、古い生成物、参考画像、個人用の入力・バックアップは整理時に削除しました。

| パス | 用途と整理の目安 |
| --- | --- |
| `src/`、ルートのJS・CSS・HTML、`manifest.json`、`presets/` | 拡張機能本体。同梱セットはindexから読み込むので、個別のファイル名をJSで検索して見つからなくても未使用ではありません |
| `icons/*.svg` と `icons/*.png` | SVGは生成元、PNGは配布用。`tools/make-icons.sh` が両方をつなぎます |
| `tools/` と `tools/tests/` | 採掘、検証、ビルド、手動診断。拡張機能から呼ばれないCLIも使います |
| `design/*.dc.html` と `design/canvas.json` | 設計の原本。canvas.jsonにアートボードが登録されています |
| `design/oshideck-card-deck-ui.html` | 設計ツールが生成する画面。生成物は削除済みで、設計原本は残しています |
| `dist/` | 再生成できるZIPとSHA-256一覧。現在の0.51.2を残し、古い版は削除済みです |
| `node_modules/` | テスト・ビルドの依存。削除後は `npm ci` で再インストールが必要です |
| `chat-*/` | 採掘バッチの候補・計画・結果・コードのスナップショット・取得データ。前回の完了済みバッチと専用の再開スクリプトは削除済みです。次回は `produce-presets.mjs --run` で新しいバッチを作ります |
| `tools/candidates/` | 旧方式の候補と生成セットは削除済みです。`scope.mjs` と `emoji-src.mjs` の既定の入力先でもあるため、使う場合は先に候補を採掘し直します |
